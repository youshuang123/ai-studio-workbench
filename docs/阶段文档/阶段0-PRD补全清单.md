## 必须问（本轮 5 个）

### 问题 1：第一版给谁用？能不能办云平台企业实名认证？

- **为什么重要**：决定要不要一开始就做多租户、RBAC、配额计费。PRD 的 FR-001 要求 owner/editor/reviewer/viewer 四角色 + 跨租户隔离，这一条会占掉 MVP 相当一部分工期。同时也决定阶段 4 上线走哪个档。
- **选项**：
  - A｜内部试用（你自己 + 3-5 人），不做企业认证 → 过渡档
  - B｜内部试用，但能办企业认证 → 生产档（可对外、可扩容），建议现在并行去办
  - C｜直接对外公开注册 → 必须生产档 + 完整 RBAC + 计费
- **推荐**：**A**。原因：MVIP 的核心风险是「AI 生成效果能不能达标」（一致性、成本），不是「能不能多租户」。先用单租户把效果跑通，RBAC 后置。
- **不选的后果**：选 C 会导致工期至少翻一倍，且效果没验证前就背上了计费、越权、审计三类线上事故风险。

### 问题 2：P0 里的 15 条功能需求，第一版砍到哪？

- **为什么重要**：PRD 的 P0 包含 M1 账号租户、M2 资产中心、M5 API 网关、M6 一致性、M7 QA、M8 后处理、M9 看板——这是一个完整 SaaS 的体量。按「一个人 + 一个 AI」的产能，全量 P0 不可能在 PRD 写的 8-10 周内完成。
- **选项**：
  - A｜只做**电商一条线**：上传 SKU → 生成主图/场景图 → 单 SKU 试跑 → 批量 → 一致性 QA → 导出
  - B｜只做**短剧一条线**：剧本 → 分镜表 → 关键帧 → 轻动效预览 → 导出
  - C｜两条线各做最小闭环（电商只做主图，短剧只做分镜+关键帧）
  - D｜按 PRD 全量 P0
- **推荐**：**A**。原因：电商线的产物是「一张图」，可以立刻用眼睛判断好坏，反馈循环最短；短剧线要经过分镜/关键帧/轻动效三层，验证周期长得多。先跑通一条线，第二条线复用同一套网关/资产中心/QA。
- **不选的后果**：选 D 会导致每条线都做一半，两个月后没有任何一条能交付给真实用户验收。

### 问题 3：¥0.10/张、¥1.00/分钟，是「你的成本」还是「卖给客户的价」？

- **为什么重要**：PRD 第 13 节自己把这条列在待确认里。成本目标和售价目标会导出完全不同的技术选型——成本 ¥0.10 只能用 FLUX schnell 这类低价 API；售价 ¥0.10 则意味着成本必须压到 ¥0.03，几乎只剩开源自托管一条路（与"不自建 GPU"冲突）。
- **选项**：
  - A｜是**成本上限**（我方花出去的钱），售价另定
  - B｜是**对外售价**，成本另算
  - C｜两者都是，成本 ≤¥0.10 且售价就是 ¥0.10（不赚钱，做规模）
- **推荐**：**A**。原因：《API优先-成本修订-v0.2.md》整份文档都是按"成本"口径测算的（含重试率、缓存命中、QA、存储），按 A 理解前后自洽。
- **不选的后果**：按 B 理解，则当前测算全部作废，且"不自建 GPU"的前提要推翻，整个方案需要重写。

### 问题 4：素材里会有真实人物、真实品牌吗？数据必须留在境内吗？

- **为什么重要**：PRD §8.3 已写了"真实人物/未成年人/品牌 logo 授权检查"，但没说**实际业务里会不会出现**。如果会，内容安全和人工复核就不是"锦上添花"，而是上线前置条件；如果只是商品图和原创角色，M7 可以大幅简化。
- **选项**：
  - A｜只有商品图和原创虚构角色，不涉及真人/真实品牌 → M7 只做基础内容安全
  - B｜会有真人（模特/演员）和真实品牌 → 需要完整授权链路 + 人工复核台
  - C｜不确定，先按 B 保守做
- **推荐**：**A**。原因：你的两条主线是"商品图"和"虚构短剧角色"，天然不涉及真人肖像；按 A 做可以省掉复核台和授权管理，直接进 P1。
- **不选的后果**：按 B 做，M7 需要额外做授权凭证管理、复核台、留痕审计，工期 +2 周起，且需要法务配合。

### 问题 5：`ai-studio-workbench-plan/mvp/` 里已有的骨架代码，作为起点还是推倒重写？

- **为什么重要**：原目录里已有一份 `mvp/` 骨架（API 网关 + 预算守卫 + 缓存 + 电商批量 + 短剧关键帧 + 8 个测试通过，`python -m studio demo` 可离线跑通）。它是 Step 5 的成果，但**不在本项目目录里**，也不符合本项目 `backend/` 的结构约定。
- **选项**：
  - A｜**对照参考，重新按本项目规范写**（保留它的设计思路和 8 个测试用例，代码重写进 `backend/`）
  - B｜直接把 `mvp/` 搬进 `backend/` 继续改
  - C｜完全不用，从零设计
- **推荐**：**A**。原因：`mvp/` 是单机 CLI 骨架（`python -m studio`），没有 HTTP 层、没有数据库、没有多租户，搬进来等于要把架构翻一遍；但它的成本守卫逻辑、网关抽象、8 个测试用例是有价值的资产，应当复用思路并搬测试。
- **不选的后果**：选 B 会带回一个与部署手册不兼容的结构（无 FastAPI、无 SQLAlchemy），阶段 4 上线时要二次重构。

## 已发现的矛盾

1. **「不自建 GPU」 vs 「P1 自托管 Wan2.2 做成本优化」**
   - PRD §7.1 说 MVP 不自建 GPU；`API优先-成本修订-v0.2.md` P1 提到"月视频量超过盈亏平衡点可自托管 Wan2.2"。
   - **裁决**：不矛盾。MVP 阶段严格 API-only；自托管是 P1 的成本优化选项，届时作为新决策重新评估（会新增服务器费用，须按规则先报价）。

2. **「完整 I2V 不作为 MVP 门槛」 vs 「FR-017 完整 I2V 批量出片（P1）」**
   - 一致，只是优先级标注。**裁决**：MVP 验收不含完整 I2V，短剧线只验收到"轻动效预览"。

3. **P0 范围与里程碑周期不匹配**
   - §3.1 列了 15 条 P0 需求，§12 却排了 8-10 周 4 个 Phase。
   - **裁决**：由问题 2 决定砍到哪条线后再重排里程碑；在范围确定前，§12 的周期不能作为承诺。

4. **D2 验收指标缺少金标集**
   - ΔE≤3 / DINO≥0.9 / ArcFace≥0.85 都是需要"标准答案"才能算的指标，PRD 未说明金标集从哪来。
   - **裁决**：按手册第十节，D2 记为「待样例打分」，阶段 2 第一次真实冒烟时用 5-10 条真实样例打分校准，不现在逼你写数字。
