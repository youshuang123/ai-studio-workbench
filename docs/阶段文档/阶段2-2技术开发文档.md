## 〇、先说清：2-2 里「一致性」怎么处理

《技术适配声明》原写「2-2 = 批量 + 一致性检查 + ZIP 导出」。实际开发时**再拆一刀**，理由写在这里：

| 子阶段 | 范围 | 你能判断什么 |
| --- | --- | --- |
| **2-2（本文档）** | CSV 导入 → 字段校验 → 试跑 1 条 → 确认 → 批量（并发 3）→ 进度 → 结果网格 → ZIP 导出 → 批次账单 | 能不能**批量**出图、花多少钱、能不能交付 |
| 2-3 | 一致性：颜色 ΔE、logo OCR、VLM 打分、图生图（参考原图） | 出的图**像不像**原商品 |
| 2-4 | 短剧线：剧本 → 分镜表 → 关键帧 | 另一条线 |

**为什么拆**：一致性需要两类 2-2 用不上的东西——① 图生图模型（当前 Z-Image-Turbo 是纯文生图，看不到上传的图）② VLM 打分（要买第二个 Key）。硬塞进 2-2 会让一个阶段里同时冒两个新变量（批量 + 一致性），出问题时无法判断是哪边坏的。

**所以 2-2 的诚实定位**：让"一次做 50 张"这件事跑通、可管、可交付；至于"每张像不像原商品"，2-3 才谈。

## 六、数据、资产与状态

### 6.1 新增表 `batches`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | TEXT(36) PK | uuid |
| `project_id` | TEXT FK | 所属项目 |
| `name` | TEXT(120) | 批次名（默认取 CSV 文件名 + 日期） |
| `status` | TEXT(24) | 见 6.2 |
| `total` | INT | 总行数 |
| `succeeded` | INT | 成功数 |
| `failed` | INT | 失败数 |
| `cost_fen` | INT | 已花（分） |
| `budget_fen` | INT | 本批预算（分） |
| `confirmed_at` | DATETIME | 用户确认批量试跑的时间（null=未确认） |
| `created_at` / `started_at` / `finished_at` | DATETIME | — |

### 6.2 状态机

**批次**

```
draft ──(试跑通过 + 用户点确认)──> queued ──> running ──> completed
  │                                              │
  └──(用户放弃)──> cancelled                     └──> stopped_over_budget / stopped_by_user
```

**批次内的行**（复用 `generation_jobs.status`，新增「跳过」）

```
queued → running → succeeded
                 ↘ failed（可重试）
                 ↘ over_budget
skipped（CSV 校验失败或缺图，不调用模型）
```

**恢复策略**：服务重启时，`batches.status` 为 `running` 的改成 `paused(INTERRUPTED)`；其下 `queued/running` 的 job 改成 `failed(INTERRUPTED)`。用户点「继续」→ 只重跑 failed/queued，**已 succeeded 的绝不重跑**（省钱，也是 PRD FR-013 的硬要求）。

### 6.3 迁移方式（`generation_jobs` 加 `batch_id`）

2-1 用的是 `create_all`，不处理已有表加列。这次引入 **Alembic**（手册第三节触发条件：出现改表需求）。

- `alembic/` + `alembic/versions/0001_add_batch_id.py`
- 迁移内容：`ALTER TABLE generation_jobs ADD COLUMN batch_id VARCHAR(36)`、新建 `batches` 表
- 启动时不自动迁移（避免线上意外），由我在开发阶段手动执行 `alembic upgrade head`，并在 README 写明

> 影响：你本机 `data/app.db` 里有 1 个冒烟项目 + 1 张图，迁移会保留它们（只加列/加表，不删数据）。

### 6.4 CSV 格式（固定表头）

```csv
sku_code,product_name,category,color,selling_points,image_file
CUP-001,316不锈钢保温杯,家居,深蓝,24小时保温,product.png
CUP-002,玻璃冷水壶,家居,透明,耐冷热,product2.png
```

| 列 | 必填 | 规则 |
| --- | --- | --- |
| `sku_code` | ✅ | 1-40 字符，批次内唯一（重复则报错） |
| `product_name` | ✅ | 1-50 字符 |
| `category` | ❌ | ≤50 |
| `color` | ❌ | ≤20 |
| `selling_points` | ❌ | ≤200 |
| `image_file` | ❌ | 与项目内已上传资产的文件名匹配；找不到 → 该行 `skipped`（提示「缺图」），**不阻断其他行** |

**编码**：先按 UTF-8-sig 读，失败再按 GBK 读；都失败 → 报「请另存为 UTF-8 或 GBK」。
**行数上限**：200 行（超出报错，避免一次点爆预算）。

**重要**：2-2 是**文生图**，`image_file` 只做归档关联，**不参与生成**。图"像不像"要等 2-3 的图生图。这一点会在界面上明说。

### 6.5 资产与导出

| 项 | 规则 |
| --- | --- |
| 生成图 | 沿用 2-1，落 `data/assets/`，同目录 `.json` 侧车 |
| 导出 ZIP | 临时目录打包，返回后删除；ZIP 不落库 |
| ZIP 结构 | `images/CUP-001.png`… + `清单.csv`（sku/名称/成本/时间）+ `账单.csv`（按模型汇总） |
| 命名 | 用 `sku_code`，不用商品名（中文文件名在部分系统会乱码） |
| 冲突 | 同 SKU 多次生成 → `CUP-001.png`、`CUP-001_2.png` |

## 七、API 设计

前缀 `/api`。错误结构不变：`{"error":{"code","message"}}`。

| # | 方法 | 路径 | 说明 |
| --- | --- | --- | --- |
| 1 | POST | `/projects/{id}/batches/validate` | 上传 CSV，返回预览 + 逐行错误（**不建批次**） |
| 2 | POST | `/projects/{id}/batches` | 用已校验的内容建批次（status=draft） |
| 3 | POST | `/batches/{id}/trial` | 试跑第 1 行（同步等结果，最长 60s） |
| 4 | POST | `/batches/{id}/confirm` | 确认批量（draft → queued） |
| 5 | GET | `/batches/{id}/events` | **SSE**：批次进度 |
| 6 | POST | `/batches/{id}/items/{item_id}/retry` | 单条重试 |
| 7 | POST | `/batches/{id}/resume` | 续跑（paused 时可用） |
| 8 | POST | `/batches/{id}/cancel` | 停止（保留已完成） |
| 9 | GET | `/batches/{id}/export` | 下载 ZIP |
| 10 | GET | `/batches/{id}` | 批次详情（含所有行） |

### 批次 SSE 事件

```
event: progress  data: {"total":20,"succeeded":7,"failed":1,"cost_fen":21,"status":"running"}
event: item      data: {"item_id":"…","sku_code":"CUP-008","status":"succeeded","cost_fen":3}
event: done      data: {"status":"completed","succeeded":19,"failed":1,"cost_fen":57}
event: error     data: {"error":{"code":"BATCH_ABORTED","message":"…"}}
```

规则：`progress` 每完成一条推一次（不轮询空转）；必须且只能以 `done` 或 `error` 收尾；心跳 10 秒。

### 校验返回示例

```json
{
  "rows": [{"index":1,"sku_code":"CUP-001","product_name":"316不锈钢保温杯","ok":true}],
  "errors": [
    {"row":7,"column":"product_name","message":"商品名称不能为空"},
    {"row":9,"column":"sku_code","message":"SKU 编码重复：CUP-001"}
  ],
  "missing_images": [{"row":12,"sku_code":"CUP-012","file":"product9.png"}],
  "total": 20,
  "valid": 18
}
```

## 十一、验收清单（你照着点）

1. **下载示例表** → 我提供 `examples/skus.csv`（20 行）
2. **上传坏表**（我另给一份：有重复 SKU、空商品名、缺图）→ 看到逐行红色错误，行号正确
3. **上传好表** → 显示「20 行，18 行可用」
4. **试跑** → 点「试跑这一条」→ 约 10 秒出图 → 显示成本 ¥0.03
5. **批量闸门** → 没试跑时批量按钮是灰的（换一个新批次验证）
6. **确认批量** → 点「确认批量（18 张 · 约 ¥0.54）」→ 进度条开始跑
7. **进度真实** → 每完成一张，网格里就多一张，数字实时变
8. **停止** → 点「停止」→ 二次确认 → 已完成的保留、未开始的变灰
9. **续跑** → 点「继续」→ 只跑剩下的

## 十二、风险与待确认

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **仍然"不像原商品"** | 你会觉得批量出的图跟商品无关 | 2-2 是文生图批量；图生图在 2-3。界面上会写一行说明，不让人误解 |
| 供应商并发限流未知 | 并发 3 也可能被 429 | 已有 `MODEL_RATE_LIMITED` 错误码；批量里 429 → 退避 2 秒重试 1 次，再失败则该行 failed 可手动重试 |
| 20 张 × 10 秒 / 3 并发 ≈ 70 秒 | 你等待时会怀疑卡住 | 进度条 + 每完成一条就出图，不用等全部 |
| 供应商可能加「AI 生成」水印 | 交付物带水印 | 2-2 先不管；2-3 评估裁剪或换供应商 |
| Alembic 首次引入 | 迁移失败会动到你的冒烟数据 | 迁移前自动备份 `data/app.db.bak`；只加列/加表 |
| ZIP 打包内存 | 200 张 × 1MB ≈ 200MB | 流式写临时文件，不整包进内存 |

**必须由产品经理决定的问题：无。**（范围、模型、预算都已在台账 D4/D10 定死；新增的 `BATCH_CONCURRENCY=3`、`BATCH_BUDGET_CNY=10` 是可改配置，不需要你审批）
